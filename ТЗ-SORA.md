## 0. КОРОТКО ДЛЯ ТОГО, КТО ПРИШЁЛ ЧИТАТЬ

Ставится **AmneziaWG** — личный VPN на собственном сервере. Клиент у
владельца уже установлен, это Amnezia.

**Всё делается двумя командами:**

```bash
bash install_sora.sh
bash sora-health.sh
```

Всё остальное в этом документе — объяснение, что делает скрипт,
что делать при неудаче и куда смотреть, если что-то пойдёт не так.

**Перед установкой владелец передаёт вам файл `server/server.conf`.**

## 1. ЧТО НУЖНО ПОСТАВИТЬ

### Обязательно

| Пакет | Зачем | Размер |
|---|---|---|
| `amneziawg-go` | сам VPN (userspace) | 3,3 МБ |
| `awg` и `awg-quick` из `amneziawg-tools` | **обязательны**, см. ниже | 150 КБ |
| `unbound` | DNS внутри туннеля | 5 МБ |
| `curl`, `ca-certificates` | загрузка | 800 КБ |
| `iptables` | NAT и правила | уже стоит |
| `jq`, `cron` | разбор JSON, автоматика | 2 МБ |
| `python3-minimal` | **учёт трафика по людям** | 25 МБ |
| `netfilter-persistent` | чтобы правила сети пережили перезагрузку | 200 КБ |

### Почему нужны `awg` и `awg-quick`, а не только бинарник

Проверено на живом сервере 15.10.2026 чтением исходников
`amneziawg-go`. Сам бинарник **не умеет читать файлы конфигурации**:
он создаёт TUN-устройство по имени интерфейса и слушает UAPI-сокет
`/var/run/amneziawg/<имя>.sock`. Настройку он получает через сокет.

Значит запустить его как `amneziawg-go --interface /etc/sora/server.conf`
нельзя: в `main.go` такого флага нет, скрипт попадает в ветку
`default`, видит `os.Args != 2`, печатает Usage и выходит.

Полный порядок запуска делает `awg-quick`:

1. `ip link add awg0 type amneziawg` — попытка через модуль ядра;
2. модуля на Debian 12 нет, поэтому fallback:
   `amneziawg-go awg0` — тот сам создаёт TUN;
3. `awg setconf awg0` — отдача конфига через UAPI;
4. `ip address add`, `ip link set up`.

Служба `amnezia-awg-go.service` поэтому вызывает `awg-quick up awg0`,
а не бинарник напрямую.

### Кириллица в идентификаторах — уже трижды за один день

Это не теория. За день установки на живом сервере кириллица в
именах переменных всплыла **три раза**, в трёх разных местах:

| Где | Что было | Как вышло наружу |
|---|---|---|
| `install_sora.sh` | `СКАЧАНО`, `кандидат` в цикле | скрипт не запустился бы |
| `awk` в тестовом скрипте | `вставлено` | `awk: unexpected character 0xd0`, файл вышел пустым |
| `note()` — не идентификатор, но по той же причине | функция печатала аргументы, а не stdin | `journalctl ... | note` давал пустоту, причина поломки была не видна |

**Чем это опасно.** `bash -n` такой код **пропускает**. Он
проверяет синтаксис и не разрешает переменные. Проверено: скрипт
с кириллицей в именах проходит `bash -n` на ура и падает только
в рантайме. То есть обычная проверка синтаксиса здесь бесполезна.

**Что делать при проверке:**

```bash
# переменные и циклы
grep -nE '^\s*[а-яА-Я_]+\s*=' install_sora.sh
grep -nE 'for\s+[а-яА-Я_]+\s+in' install_sora.sh
# awk внутри скриптов
grep -nE "awk '.*[а-яА-Я]" install_sora.sh
```

Все имена — латиницей. Русским можно писать **комментарии и
сообщения пользователю**, но не идентификаторы.

### Модуля ядра нет — и это нормально

Ядро `6.1.0-53-amd64` содержит только обычный WireGuard
(`CONFIG_WIREGUARD=m`), модуля `amneziawg` в нём нет
(`modprobe amneziawg` → `Module not found`). Поэтому работает
userspace-реализация. Она медленнее модуля, но для личного VPN
на 1 ядре разницы не видно.

Следствие для настройки службы: `PrivateDevices=yes` использовать
**нельзя** — он даёт процессу приватный `/dev` без `/dev/net/tun`,
и туннель не поднимется. `CapabilityBoundingSet` тоже не может быть
пустым: нужна `CAP_NET_ADMIN`.

### Почему Python всё-таки ставится

В версии 1.0 ТЗ было написано: «Python на сервере не нужен,
генератор работает на компьютере владельца». **Это было верно, пока
не существовало учёта трафика.**

Учёт по людям нужен, чтобы видеть расход месячного литра и
ограничивать отдельно взятых людей. На shell такую арифметику с
помесячным переходом, обработкой сброса счётчиков и применением
лимитов писать дольше и опаснее, чем на Python.

`python3-minimal` — это ~25 МБ и ~10 МБ памяти в момент запуска,
раз в 5 минут. На чистом сервере с 600 МБ свободных это не заметно.

**Генератор ключей при этом по-прежнему работает на компьютере
владельца.** Python на сервере нужен только для учёта трафика.

### Ставить нельзя

| Пакет | Почему |
|---|---|
| **Docker** | 400–500 МБ только на себя |
| ~~**python3**~~ | ~~генератор ключей работает на компьютере владельца~~ |
| **fail2ban** | ощутимо по памяти; если понадобится — поставим точечно |

### nginx

**Не нужен для VPN.** AmneziaWG работает по UDP, nginx — это HTTP.
Они не пересекаются.

Если трекеру понадобится nginx — это отдельная задача, в этом ТЗ её
нет.

## 2. ЧТО ИЗВЕСТНО О СЕРВЕРЕ

| Параметр | Значение |
|---|---|
| ОС | Debian 12 (x86_64) |
| Ядер | 1 |
| Память | 768 МБ всего, ~600 МБ свободно после очистки |
| Диск | 9 ГБ, ~5,9 ГБ свободно |
| Трафик | 4000 ГБ/мес |
| IP | `203.0.113.10` (Москва, AS205090) |
| IPv6 | адрес есть, маршрута нет, наружу не работает |
| Что останется | трекер сайтов |

### Про память — важно для планирования

VPN (`amnezia-awg-go`) ест **около 20 МБ** в покое. Потолок `MemoryMax`
выставлен на **100 МБ** — это не «чтобы не мешал трекеру», а чтобы при
всплеске трафика ядро убило **VPN**, а не трекер. Потолок срабатывает
только при аномалии.

### Про IPv6

IPv6 на сервере не маршрутизируется: адрес `2ac:5d0:312::dec/48`
назначен с флагом `noprefixroute`, `curl -6` возвращает код 7.
Проверено, это не настройка, которая «включится сама».

Поэтому в конфигурации клиента `AllowedIPs = 0.0.0.0/0, ::/0` —
 IPv6 уходит в туннель и там гаснет. Без этого IPv6-трафик шёл бы
мимо туннеля напрямую, и провайдер видел бы настоящий адрес.

## 4. УСТАНОВКА

### 4.1. Положить конфигурацию

Владелец передаёт файл `server/server.conf`. Положите его:

```bash
mkdir -p /etc/sora
chmod 700 /etc/sora
# и скопируйте файл сюда
chmod 600 /etc/sora/server.conf
```

**Внимание.** Файл содержит **приватные ключи всех пользователей**.
Права 600, только root. Не пересылайте его дальше и не кладите
в общие каталоги.

### 4.2. Запустить установку

```bash
cd /путь/к/папке/SORA/server
bash install_sora.sh
```

Скрипт сам:

1. проверит память, место и свободность порта;
2. поставит пакеты;
3. скачает `amnezia-awg-go`;
4. включит пересылку пакетов;
5. настроит резолвер DNS и проверит его конфигурацию;
6. откроет **один** порт — `39117/UDP`;
7. создаст службу с ограничениями доступа;
8. запустит таймер проверки каждые 5 минут;
9. проверит, что всё работает и что ничего не сломалось;
10. **при любой неудаче откатит сам.**

### 4.3. Что скрипт НЕ делает

- не перезагружает сервер;
- не ставит Docker;
- не трогает nginx и трекер;
- не меняет настройки ядра, кроме пересылки пакетов;
- не удаляет ни одного существующего правила iptables.

## 6. ЗАЩИТА ОТ УТЕЧЕК

### DNS

Без `unbound` DNS-запросы шли бы мимо туннеля, и провайдер видел бы
все домены, которые открывает пользователь. Это самая частая утечка
в самодельных VPN.

Резолвер слушает **только** `10.77.0.1:53`, доступ разрешён **только**
из подсети туннеля, всё остальное — `refuse`.

#### Куда класть конфиг — и почему это легко упустить

Проверено на живом сервере 15.10.2026. Конфиг резолвера **обязан**
лежать в `/etc/unbound/unbound.conf.d/sora.conf`. Настоящее
расположение Debian 12 — этот каталог, он подключается из
`unbound.conf` через `include`.

Если положить конфиг рядом с VPN, например в `/etc/sora/unbound.conf`,
то **`unbound` его никогда не прочитает**. Служба возьмёт свой штатный
конфиг Debian и станет слушать `127.0.0.1:53` вместо `10.77.0.1:53`.

Выглядит это так — и в этом главная опасность:

```
[ok] sluzhba rabotaet               <- unbound активен
[!!] rezolver ne slushaet na 10.77.0.1:53
```

То есть «служба работает» и «DNS в туннеле не работает» — одновременно,
без всякой связи между строками. Первое сбивает с толку, второе
объясняет поломку. Проверять надо именно `ss -lunp | grep :53`.

#### Порядок запуска

Резолвер вешается на адрес туннеля. Пока `awg0` не поднят, адреса
`10.77.0.1` не существует, и `unbound` не сможет на него слушать.
Поэтому в юните задано:

```
After=amnezia-awg-go.service
Requires=amnezia-awg-go.service
```

### IPv6

Закрыт через `AllowedIPs = 0.0.0.0/0, ::/0`, как описано в разделе 2.

### Проверка после подключения

```bash
# на ноутбуке, при подключённом VPN
curl https://whatismyipaddress.com     # ждём 203.0.113.10
curl https://ipleak.net                 # DNS-серверы не из России
```

## 5a. СОХРАНЕНИЕ ПРАВИЛ: НЕДОВЕДОМЫЙ ПАКЕТ

Это раздел, который ломается тихо и дорого.

### Что происходит

`netfilter-persistent` на Debian 12.15 ставится, включается, отвечает
на команды кодом 0 — и **ничего не делает**.

Проверено на живом сервере:

```bash
dpkg -L netfilter-persistent | grep plugins.d
# /usr/share/netfilter-persistent/plugins.d     <- только каталог, ФАЙЛОВ НЕТ

netfilter-persistent save
# код 0, /etc/iptables/ остаётся пустым
```

Весь скрипт `/usr/sbin/netfilter-persistent` состоит из одной мысли:

```bash
run_plugins () {
    if [ -d ${PLUGINS} ]; then
        run-parts -v -a ${1} ${PLUGINS}
    fi
}
```

Он запускает всё, что лежит в каталоге плагинов. Каталог пуст — значит
ни `save`, ни `start` не делают ничего, но выходят с кодом 0.
**Выглядит как успех.**

### Что будет если не заметить

Правила `iptables` живут в памяти. Месяц всё работает. Потом сервер
перезагружается — и VPN молча умирает: NAT пропал, DNS умер,
счётчики исчезли. А `netfilter-persistent` при этом «установлен»,
и проверка его наличия проходит.

### Решение

Плагины пишутся вручную — это два коротких скрипта:

- `/usr/share/netfilter-persistent/plugins.d/iptables`
- `/usr/share/netfilter-persistent/plugins.d/ip6tables`

Делают ровно то, что делает штатный: `iptables-restore` при старте,
`iptables-save` при сохранении, очистка при `stop`.

### Как убедиться, что работает

Проверка настоящая, а не «файл существует»:

```bash
iptables-save > /tmp/страховка.rules      # на всякий случай
iptables -F && iptables -X                 # сносим всё
systemctl restart netfilter-persistent
iptables -t filter -S | grep SORA-TRAFFIC  # правила вернулись?
```

Если цепочки на месте — перезагрузка безопасна. Выполнено на живом
сервере 15.10.2026: после полной очистки правила восстановились.

## 7a. УЧЁТ ТРАФИКА ПО ЛЮДЯМ

### Зачем

На сервере есть месячный лимит трафика: 4000 ГБ. Без учёта
непонятно, сколько израсходовано и сколько останется.

**Cloudflare WARP этого не умеет.** Он не различает пользователей и
не отдаёт статистику по ним. Учёт по людям — второе, ради чего
SORA строится вместе с уже работающим WARP.

Учёт нужен для трёх вещей:

- знать, сколько трафика осталось до конца месяца;
- ограничивать отдельно взятых людей, чтобы один не съел весь
  месячный объём;
- видеть, кто пользуется, а кто нет.

### Как считается

Счётчики байтов вешаются на каждого пользователя в цепочке `FORWARD`
через `iptables`. Это не зависит от того, какая реализация VPN стоит:
метод одинаково работает и для `amnezia-awg-go`, и для обычного
WireGuard, и для любой будущей замены.

**Счётчики не обнуляются.** Запоминается последнее прочитанное
значение, трафик считается как разница. Обнуление на работающем VPN
гоняется с гонкой: между чтением и обнулением может пройти пакет, и
он будет учтён дважды или потерян. Разница абсолютных значений такой
ошибки не даёт.

### Помесячный переход — место, где легко испортить счёт

Счётчики `iptables` живут вместе со службой и **при смене месяца не
обнуляются**. Новое состояние начинается с нуля, а счётчик
показывает прошлый месяц. Разница «прошлый месяц минус ноль» равна
целому прошлому месяцу. Итог удваивался бы, и при попытке
сверить с логом провайдера цифры не сошлись бы никогда.

Поэтому первый опрос нового месяца **только запоминает базу** и не
прибавляет ничего. Это проверено тестом.

### Лимиты

Лимитов по умолчанию нет: трафик просто считается.

```bash
sora_traffic.py limit ivan 100      # 100 ГБ в месяц
sora_traffic.py limit --list        # показать все лимиты
sora_traffic.py limit ivan          # снять лимит
```

Превысивший **не удаляется**, а помечается в `blocked.json` и
убирается из конфига сервера. Обратимо:

```bash
sora_traffic.py status             # кто отключён
sora_traffic.py restore ivan       # вернуть
```

### Что делает отключение

`sora_traffic.py apply` правит файл, который читает работающий VPN.
Порядок жёсткий:

1. резервная копия **до** изменений;
2. новый текст собирается целиком и проверяется разбором;
3. если хоть один отключаемый остался в тексте — **отказ**;
4. если ничего не изменилось — VPN не перезапускается зря;
5. после записи проверяется, поднялась ли служба; если нет —
   конфиг возвращается обратно.

### Автоматика

```bash
*/5 * * * *  sora_traffic.py poll
```

Пять минут — компромисс. Чаще точнее, но чаще и накладные расходы;
реже — крупнее пауза до отключения. На точность счёта в байтах
частота не влияет.

## 7b. РЕЗЕРВНОЕ КОПИРОВАНИЕ

### Почему это срочно

В `/etc/sora/server.conf` лежат **приватные ключи всех
пользователей**. Потеря файла = потеря доступа у всех, кто когда-либо
подключался. Ключи не восстанавливаются: их можно только
сгенерировать заново, и тогда старые конфиги людей перестанут
работать.

### Куда

`/var/backups/sora/дата-время/`, права каталога 700, файлов 600.
Ротация: последние 30 копий, старые удаляются.

**Копии остаются на том же сервере.** Копия на другом сервере — это
уже не резервная копия, а передача приватных ключей третьим лицам.

### Что копируется

`server.conf`, лимиты, список отключённых, конфиг резолвера, счётчик
трафика, список служб трекера.

### Команды

```bash
sora_backup.sh              # создать копию
sora_backup.sh list         # показать копии
sora_backup.sh restore КАТ # вернуть из копии
sora_backup.sh cleanup      # удалить старые
```

`restore` спрашивает подтверждение, показывает что собирается
заменить, сохраняет текущее состояние в отдельную копию и
перезапускает VPN. Если перезапуск не удался — сообщает об этом.

### Автоматика

```bash
17 4 * * *  sora_backup.sh
```

Первая копия создаётся сразу при установке. Иначе первую же ночь,
когда копии ещё нет, можно потерять `server.conf`.

## 7c. ПРОВЕРКА С КЛИЕНТА

### Зачем своя, если есть Amnezia

Ни Amnezia, ни WARP, ни любой другой клиент не умеют сказать, **чем
именно обернулось** подключение. Они умеют подключиться. Проверка
умеет показать, что получилось.

Она не зависит от того, чем вы подключились: Amnezia, чужой клиент
или будущий наш.

### Что проверяет

| Проверка | О чём |
|---|---|
| C0 | включён ли Cloudflare WARP, где выход |
| C1 | какой внешний адрес виден |
| C2 | работает ли туннель SORA, или защищает WARP |
| D1 | утекает ли DNS мимо туннеля |
| E1 | утекает ли IPv6 мимо туннеля |
| F1 | доходит ли трафик до сервера |
| G1 | скорость через туннель |
| H1 | есть ли kill switch |

### Различает WARP и SORA

Если включён WARP, а SORA не подключён, проверка пишет **«трафик
защищён, это не поломка»**. Первая версия так не умела и объявляла
утечкой адрес Cloudflare, который на самом деле шёл через туннель.

То же с IPv6: адрес `2a09:bac5::` — это WARP, он идёт через
туннель. **Утечка** — это когда IPv6 идёт мимо туннеля.

### Запуск

```bash
python sora_client_check.py --подробно
python sora_client_check.py --html otchet.html
```

5. Открыть любой сайт — грузится.

### Автоматическая самопроверка

Всё перечисленное выше проверяет **состояние**: живо ли, есть ли
место. Отдельная проверка смотрит на **правильность установки**:

```bash
sora-selftest.sh
```

Она видит то, чего не видит проверка состояния:

- счётчики трафика заведены на **каждого** пользователя, а не только
  цепочка создана;
- у каждой секции `[Peer]` есть имя — без него учёт не знает, кому
  принадлежит трафик, и припишет его ничему;
- права на копии ключей — 600, на каталог — 700;
- `Restart=on-failure` и автозапуск включены;
- три задачи в `/etc/cron.d/sora` на месте;
- правила сети сохранены и переживут перезагрузку;
- трекер из `tracker.services` работает.

**Почему это отдельная проверка.** Установка может закончиться
кодом 0, всё зелёное — а счётчики не создались. Тогда месяц VPN
работает, люди подключаются, а трафик не посчитан ни байтом.
Проверка состояния такое не заметит: служба-то жива.

Установщик запускает самопроверку последним шагом и говорит, если
что-то найдено.

### Критерий приёмки

Все проверки раздела 7 пройдены **и** `sora-selftest.sh` прошёл
**и** клиентская проверка на ноутбуке прошла. Иначе — раздел 11.

## 9. ПОРТЫ ДЛЯ ТРЕКЕРА

**Самое важное в этом разделе: трекеру для сбора данных НУЖЕН
исходящий трафик, а не входящий.**

Трекер ходит к сайтам — то есть **сам** подключается наружу. Ему не
нужно ни одного открытого порта. Если вы открыли порт «на всякий
случай», вы просто добавили вход в сервер.

Открывать порт нужно **только если** вы делаете публичную страницу
со статистикой или API.

### Как открыть

```bash
bash sora-open-port.sh 443 tcp "treker — publichnyy sayt"
```

Скрипт добавит правило **и сохранит его**, чтобы порт не закрылся
после перезагрузки.

### Как закрыть

```bash
bash sora-close-port.sh 443
```

### Обязательно после установки

```bash
apt install -y netfilter-persistent
netfilter-persistent save
```

Без этого все правила iptables **исчезнут при перезагрузке**, и VPN
не запустится. Установщик об этом предупреждает.

### Проверить трекер в проверке состояния

Чтобы `sora-health.sh` следил и за трекером, создайте файл:

```bash
echo treker > /etc/sora/tracker.services
```

Скрипт будет проверять каждую службу из этого файла и кричать,
если она упала.

## 10. ОТКАТ

```bash
bash uninstall_sora.sh
```

Скрипт спросит подтверждение, покажет что собирается сделать,
затем:

- остановит VPN и таймеры;
- удалит `/etc/cron.d/sora` — **иначе сервер каждые 5 минут будет
  искать файлы, которых уже нет**, и в журнале пойдёт шум, в
  котором утонет любая настоящая поломка;
- восстановит правила сети **из снимка, сделанного до установки**;
- вернёт `net.ipv4.ip_forward` в исходное состояние;
- удалит службы, конфигурацию и бинарник;
- проверит, что трекер жив.

**Трекер и прочие службы не трогаются.**

**История трафика в `/var/lib/sora` остаётся.** Там помесячные
срезы статистики. Удаляется вручную, когда будет больше не нужна.

> Если после отката выяснится, что `ip_forward` был не нужен, верните
> его в 0: `sysctl -w net.ipv4.ip_forward=0`.

## 12. ЕСЛИ НЕ СКАЧАЛСЯ VPN

### 12.1. Почему он не скачивается

**Проверено на живом сервере 15.10.2026.** Репозиторий
`amnezia-vpn/amneziawg-go` **не имеет ни одного релиза** — там только
исходники. Любая ссылка вида `releases/latest/download/...` на нём
возвращает `404`. Готовой сборки в удобном месте не существует.

Проверить можно так:

```bash
curl -s https://api.github.com/repos/amnezia-vpn/amneziawg-go/releases | head -c 60
# выведет [] — релизов нет
```

Поэтому установщик сначала ищет бинарник на самом сервере и только
потом пробует скачать. Если скачать нечего — он скажет об этом и
остановится, а не поставит что-нибудь не то.

### 12.2. Что делать

1. **Не подменяйте пакет** обычным `wireguard-tools` и не ставьте
   `openvpn`. Это другие протоколы, они не замаскированы и будут
   опознаны оборудованием провайдера. Тогда VPN не оправдывает себя.
2. **Положите на сервер `awg` и `awg-quick`**, иначе установщик
   остановится с сообщением об этом. Берутся из архива релиза
   `amneziawg-tools` (`ubuntu-22.04-amneziawg-tools.zip`, проверено:
   бинарники работают на Debian 12):

   ```bash
   scp awg awg-quick root@203.0.113.10:/root/sora/bin/
   ```

3. Проверьте доступность GitHub: `curl -sI https://github.com | head -1`
4. **Соберите `amneziawg-go` на своём компьютере** (не на сервере):

   ```bash
   git clone https://github.com/amnezia-vpn/amneziawg-go
   cd amneziawg-go
   GOOS=linux GOARCH=amd64 CGO_ENABLED=0 go build -trimpath \
       -o amneziawg-go-linux-amd64 .
   ```

   Требуется **Go 1.25 или новее** (в `go.mod`: `go 1.25.0`).
   Debian 12 содержит Go 1.19 — недостаточно.

5. Передайте бинарник на сервер:

   ```bash
   scp amneziawg-go-linux-amd64 root@203.0.113.10:/root/sora/
   ```

   Именно в `/root/sora/` — установщик ищет файл
   `amneziawg-go-linux-amd64` в этом каталоге и в `/tmp`.

6. Повторите `bash install_sora.sh` — он увидит готовый бинарник.

**Не собирайте из исходников на сервере.** На маске в 708 МБ
компилятор Go вместе с работающим трекером и nginx вызывает OOM,
и виновником оказывается не сборка, а nginx — сайт падает.

### 12.3. Про S1 и S2 — ошибка была в генераторе, не в установщике

`S1` и `S2` в AmneziaWG — это **размеры** (uint16, 0…65535), а не
произвольные 32-битные числа. Так их и читает настоящий `awg`:

```c
ret = parse_uint16(&ctx->device->init_packet_junk_size, "S1", value);
...
if (*end || ret > UINT16_MAX) {
    fprintf(stderr, "Unable to parse %s: `%s'\n", name, value);
    exit(1);
}
```

Если сгенерировать `S1 = 3295741239`, сервер отвергнет конфиг
на `awg setconf` и установка упадёт на последнем шаге.
`H1`…`H4` идут через `u32_range_from_string`, там 32 бита — им
диапазон не мешает.

## 13. ИЗВЕСТНЫЕ ОГРАНИЧЕНИЯ

Честно о том, что может не сработать.

| Ограничение | Следствие |
|---|---|
| AmneziaWG работает **только по UDP** | если сеть режет UDP — решения в этом ТЗ нет, нужен другой протокол |
| Адрес **один**, ротации нет | при блокировке адреса — отдельная задача, нужен второй сервер |
| 1 ядро | скорость упирается в домашний канал, а не в сервер |
| IPv6 не маршрутизируется | учтено: утечки нет, но и IPv6-сервисы через VPN не работают |
| Задержка до сервера — **6 мс** | не заметно, сервер рядом с вами |
