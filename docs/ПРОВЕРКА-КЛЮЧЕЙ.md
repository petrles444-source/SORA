# Проверка ключей: офлайн-анализ и живой стенд

Два инструмента, которые решают разные задачи. Первый работает без
сети вообще, второй поднимает настоящий туннель в контейнере.

| | `sora_keyscan.py` | `sora_warpcheck.py` |
|---|---|---|
| Что делает | разбирает конфиги, ищет дубли и мусор | поднимает туннель, ждёт рукопожатия |
| Сеть | **не нужна совсем** | нужен интернет |
| Docker | не нужен | нужен |
| Отвечает на вопрос | «какие ключи у меня вообще есть» | «отвечает ли сервер с этого адреса» |
| Время на ключ | миллисекунды | 10–35 секунд |

Начинать надо с первого: он бесплатный по времени и сразу
показывает, есть ли смысл проверять второй.

---

## 1. Офлайн-анализ: `sora_keyscan.py`

Разбирает папку с конфигами `.conf`, собирает статистику и **ни
одного байта наружу не отправляет**. Это не обещание — в файле
нет ни одного сетевого импорта:

```powershell
python -c "import ast,io;print(sorted({n.names[0].name for n in ast.walk(ast.parse(io.open(r'tools/sora_keyscan.py',encoding='utf-8').read())) if isinstance(n,ast.Import)}))"
```

Выведет список вроде `['argparse', 'json', 'pathlib', ...]`.
Ни `socket`, ни `requests`, ни `urllib`, ни `subprocess` в нём
нет — проверить можно одной командой выше.

### Запуск

```powershell
python tools/sora_keyscan.py C:/путь/к/конфигам
python tools/sora_keyscan.py C:/путь/к/конфигам --все
```

### Что он показывает

- сколько конфигов, сколько **уникальных** открытых ключей
- в каких зонах и на каких серверах они живут
- какие версии формата (`v1`, `v2`, `v3`) встречаются
- старые ли это файлы, есть ли дубли и «мёртвые» остатки

Дубли — нормальное дело: мобильные приложения любят
перегенерировать конфиг при переустановке. Ключ при этом
остаётся тем же самым, поэтому 100 файлов могут содержать 8
уникальных ключей.

## 2. Живой стенд: `sora_warpcheck.py`

Поднимает настоящий туннель AmneziaWG **внутри одноразового
контейнера Docker** и гасит его. Основная сеть машины и
основной AmneziaWG не затрагиваются.

### Требования

- Docker Desktop запущен
- около 120 МБ на образ (собирается один раз, дальше из кэша)
- Linux или Windows + WSL2

### Проверка одного ключа

```powershell
python tools/sora_warpcheck.py C:/путь/к/конфигам/example.conf
```

### Проверка всех ключей в папке

```powershell
# каждый файл, с паузой, чтобы не нагружать сервер
python tools/sora_warpcheck.py --папка C:/конфиги --pause 25

# только уникальные ключи, новые сверху — обычно их в разы меньше
python tools/sora_warpcheck.py --папка C:/конфиги --только-уникальные --pause 25
```

### Что он печатает

```
  сервер:   31.76.110.142:3854
  I1:       есть

  вердикт:  ОТПРАВИЛ, НЕ ОТВЕТИЛ
    · transfer: 0 B received, 2.05 KiB sent
    · 3 packets transmitted, 0 received, 100% packet loss
    · пакеты шифруются и уходят, ответа нет
```

Приватные ключи не показываются никогда — ни в выводе, ни в
JSON-отчёте. Перед запуском печатается конфиг, который уйдёт в
контейнер, со скрытыми ключами: можно глазами убедиться, что
передалось именно то, что нужно.

### Как читать вердикт

| Вердикт | Что значит |
|---|---|
| `ОТВЕТИЛ` | сервер ответил на рукопожатие. Ключ рабочий **с этого адреса** |
| `ОТПРАВИЛ, НЕ ОТВЕТИЛ` | туннель работает, пакеты шифруются и уходят, ответа нет |
| `НЕ ОТВЕЧАЕТ` | пакеты не уходили — смотреть детали |
| `КОНФИГ НЕ ПРИНЯТ` | устройство не приняло конфиг |
| `НЕ ПОДНЯЛСЯ` | туннель не создался, смотрите детали |
| `БИТЫЙ КОНФИГ` | в файле нет обязательных полей |

## 3. Главное ограничение: адрес, а не ключ

Стенд отвечает на вопрос «**отвечает ли сервер с этого адреса**».
Он не отвечает на вопрос «работает ли ключ». Разница существенна.

Часть публичных генераторов WARP требует регистрации реального
адреса через бота в Telegram и отдаёт конфиг только на
зарегистрированные адреса. Ключ, прекрасно работающий с
телефона, из контейнера не ответит — и это скажет не о ключе, а
об адресе.

Поэтому `ОТПРАВИЛ, НЕ ОТВЕТИЛ` читается как «сервер не ответил
с этого адреса». Ни больше, ни меньше.

Практический вывод: **стенд годится для проверки собственных
серверов и ключей, выданных на ваш адрес.** Для ключей чужих
генераторов он покажет «не отвечает» почти всегда, и это
информация об их политике, а не о ключе.

## 4. Почему так много странностей в реализации

Раздел оставлен намеренно: каждый пункт стоил реального
отладочного прогона, и каждый выглядит как «очевидная ошибка»,
пока не столкнёшься.

**Контейнер делит ядро с хостом.** Образ ядро не меняет:
`alpine` и `debian:bookworm-slim` внутри показывают одно и то же
`uname -r`. Поэтому сообщение

```
Running amneziawg-go is not required because this kernel has
first class support for AmneziaWG
```

не зависит от образа. **Это уведомление, а не ошибка.** Загуглив
его, легко решить, что бинарник сломан, и потратить день на
перебор образов.

**Конфиг не передаётся через stdin.** `amneziawg-go` принимает
конфиг на stdin, но в этой версии **не передаёт его устройству**.
Туннель поднимается пустым: пира нет, шифровать нечего.

Это самая коварная поломка в списке, потому что **выглядит как
работающий туннель**. Счётчик исходящих байтов растёт — их пишет
ядро в TUN независимо от того, читает ли их кто-нибудь. Снаружи
это неотличимо от «ключ отправил, сервер молчит».

Правильно — через UAPI-сокет, после запуска процесса:

```sh
amneziawg-go wgt &
awg setconf wgt /warp/peer.ini
```

**`awg setconf` требует заголовок `[Interface]`.** Без него
парсер отвечает `Line unrecognized` на первую же строку.

**`Address` с IPv6 через запятую не принимается.** Строка
`Address = 172.16.0.2,2606:4700:…` даёт `Configuration parsing
error`. Поле нам и не нужно: адрес на туннеле назначается
самим стендом.

**Строка `peer:` в `awg show` начинается в колонке 0.** Остальные
поля интерфейса сдвинуты на два пробела. Проверка вида
`grep '^  peer:'` не срабатывает **никогда** и объявляет
исправный туннель пустым.

**`kill -0 $PID` в конвейере врёт.** В конструкции
`( sleep 600 ) | amneziawg-go &` переменная `$!` указывает не на
процесс `amneziawg-go`, и проверка живости даёт «умер» при живом
процессе. Настоящая проверка:

```sh
pidof amneziawg-go      # возвращает PID
awg show wgt            # отвечает, если сокет жив
```

**Маршрут по умолчанию надо ЗАМЕНЯТЬ, а не добавлять.** У
контейнера уже есть свой `default` с меньшей метрикой. Добавленный
без удаления старого не сработает, и пакеты уйдут мимо туннеля.
Хуже всего, что при этом `ping` может давать 0% потерь: если
маршрут не переключился, трафик просто идёт обычной дорогой
контейнера. Выглядит как полный успех, а туннель не участвовал.

**`amneziawg-go` живёт, пока жив stdin.** Конструкция
`cat wg.conf | amneziawg-go wgt` закрывает трубу сразу после
`cat`, и процесс уходит на EOF. Надёжный способ:

```sh
( sleep 600 ) | amneziawg-go wgt &
```

**`--cap-add NET_ADMIN` недостаточно.** Нужно ещё пробросить
устройство:

```sh
docker run --cap-add NET_ADMIN --device /dev/net/tun ...
```

Без второй строки бинарник падает с
`/dev/net/tun does not exist`. Право не создаёт файл устройства.

**`debian-slim` не содержит `ip` и `ping`.** Ставятся так:

```dockerfile
RUN apt-get update \
 && apt-get install -y --no-install-recommends iproute2 iputils-ping \
 && rm -rf /var/lib/apt/lists/*
```

**Имя сервера резолвится на хосте.** Внутри контейнера DNS может
не работать, а нерезолвенное имя означает «пакет не ушёл» — то
есть ложный отрицательный вердикт.

**Счётчики TUN не доказывают шифрование.** `TX` растёт от того,
что ядро записало пакет в устройство. Единственный честный
признак того, что туннель рабочий, — `transfer:` в `awg show`
и `latest handshake`.

**Отбор «по ключу» должен идти по PrivateKey, а не по PublicKey.**
Поле `PublicKey` в секции `[Peer]` принадлежит **серверу**, и у
всех конфигов одного генератора оно одинаковое. Отбор по нему
схлопывает 126 файлов в один ключ и тихо теряет остальные.

Признак, по которому это видно: запрошено «уникальные ключи»,
а в отчёте их 1, хотя файлов больше сотни.

Личность ключевой пары задаёт приватный ключ — он уже есть в
файле и однозначен. Считать публичный из приватного не нужно.

## 5. Проверка, что стенд не врёт

Правило, которое стоит применять всегда: **сначала возьмите
заведомо рабочий ключ и убедитесь, что стенд его одобрил.**

Если эталонный ключ признан мёртвым — виноват стенд, а не ключ.
Все перечисленные ниже ошибки проверены на практике:

| Симптом | Настоящая причина |
|---|---|
| `НЕ ПОДНЯЛСЯ` при живом ключе | `ip` не установлен, маршрут не переключён |
| 0% потерь, но рукопожатия нет | пинг шёл мимо туннеля, обычной дорогой |
| `КОНФИГ НЕ ПРИНЯТ` при верном ключе | нет `[Interface]` или `Address` с IPv6 |
| пир не грузится, байты идут | конфиг ушёл в stdin, а не в UAPI |
| процесс «умер», сокет отвечает | `$!` в конвейере указывает не на тот PID |
| вердикт «не отвечает» при отправленных байтах | разбор строки `transfer` нарезался не по тому разделителю |
| «уникальных ключей: 1» из 126 файлов | отбор шёл по серверному `PublicKey`, а он у всех одинаковый |

## 6. Этика и границы

Стенд проверяет **ваши собственные** конфиги — те, что вы получили
или сгенерировали сами.

Чего инструмент не делает и не должен делать:

- не сканирует чужие хосты и порты
- не перебирает ключи и не подбирает чужие
- не долбит сервер: один контейнер, один ключ, пауза между

Особенно про порты: у части провайдеров виртуальных серверов
сканирование с их адреса приводит к блокировке IP и отключению
всей VPN-сети разом. Стенду это не нужно — он обращается ровно к
одному адресу, который сам указан в вашем конфиге.

---

## 7. Что дальше

Для клиентов это не нужно. Клиент получает готовый конфиг и
импортирует его в приложение Amnezia — одним нажатием. Стенд
существует для разработчика: убедиться, что ключ рабочий,
прежде чем отдавать его кому-то ещё.
