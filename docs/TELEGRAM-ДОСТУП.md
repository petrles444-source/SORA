# Доступ к Telegram Bot API с VPS

Настоящая запись. Всё в ней измерено на реальном сервере, цифры не
переписаны «на глаз».

---

## Коротко

Бот на российском VPS не отвечает. Причина почти всегда не та, какой
её сначала считают, и лечится без обращения к хостеру.

| Что кажут | Что на самом деле |
|---|---|
| «Хостер заблокировал Telegram» | Заблокирован один адрес из нескольких |
| «Сервер заблокирован в Telegram» | ICMP проходит, режется только TCP/443 |
| «Надо жаловаться хостеру» | Правится одним правилом DNAT |

---

## Что измерено

Debian 12, VPS в российском дата-центре. Дата замеров — 15.10.2026.

### Адреса Telegram

| Адрес | TCP/443 | HTTPS |
|---|---|---|
| `149.154.166.110` | таймаут 12 с | — |
| `149.154.167.220` | открыт | **отвечает, 150 мс** |
| `149.154.167.198` | таймаут | — |
| `149.154.175.100` | таймаут | — |
| `91.108.56.130` | открыт | не отвечает |

Два адреса из пяти работают. Значит блокировка не «Telegram целиком»,
а выборочная, и обойти её можно, не выходя из своего железа.

### Фильтр не про Telegram

| Хост | Результат |
|---|---|
| `github.com:443` | отвечает |
| `cloudflare.com:443` | отвечает |
| `google.com:443` | таймаут |

Google закрыт наравне с Telegram. Фильтр выборочный по назначению,
и «проблема Telegram» — лишь одно из его проявлений.

### Это не бан по адресу

```
                       rtt min/avg/max/mdev = 47.767/47.895/48.024/0.128 ms
```

Хост достижим. Режется конкретно TCP/443 до него.

## Почему не срабатывает `/etc/hosts`

Самое естественное решение — дописать рабочий адрес в `/etc/hosts`.
На проверенном хосте **оно не работает**, и это отдельная находка,
которую стоит знать, потому что часов на неё уходит больше всего.

```
/etc/nsswitch.conf:   hosts: files dns       <- файлы идут первыми, всё верно
od -c /etc/hosts      "api.telegram.org 149.154.167.220\n"   <- синтаксис верный
getent hosts test.local        -> 1.2.3.4   <- /etc/hosts читается
getent hosts api.telegram.org  -> 149.154.166.110   <- и всё равно DNS

curl -v https://api.telegram.org/
  *   Trying [2001:67c:4e8:f004::9]:443...
  *   Trying 149.154.166.110:443...
```

Порядок источников правильный, запись разбирается верно, механизм
резолвера файл читает — и всё равно имя уходит в DNS.

Причина в порядке ответа. Система возвращает **AAAA раньше A**, и
соединение уходит на IPv6, который на этом хосте сломан (шлюз
`FAILED`). До IPv4 дело не доходит, а `/etc/hosts` про адрес не
подменяет ничего, потому что решение уже принято.

**Правило, которое из этого следует.** Если резолвер отдаёт IPv6
раньше IPv4, правка `/etc/hosts` бесполезна. Помогает только
вмешательство на уровне пакетов.

## Что делает инструмент

`tools/sora_telegram.py`. Четыре подкоманды:

```bash
python3 tools/sora_telegram.py check     # выяснить, что сломано, ничего не меняя
sudo   python3 tools/sora_telegram.py fix # найти рабочий адрес и включить перенаправление
sudo   python3 tools/sora_telegram.py verify
sudo   python3 tools/sora_telegram.py revert
```

Ничего устанавливать не нужно: стандартная библиотека Python 3,
`iptables`, `systemctl`. На Debian 12 всё это уже есть.

### Как именно чинит

Правило DNAT в цепочке `OUTPUT` таблицы `nat`:

```
-p tcp -d 149.154.166.110 --dport 443 -j DNAT --to-destination 149.154.167.220:443
```

Имя не участвует вообще — результат не зависит от того, как система
разрешает имена, а это и есть исходная поломка.

SNI остаётся `api.telegram.org`, сертификат проверяется как обычно.
Перенаправляется только TCP/443 к одному адресу.

### Почему проверяют не порт, а ответ

Порта мало. У `91.108.56.130` порт 443 открыт, а HTTPS не отвечает
вообще. Поэтому инструмент идёт до конца: делает настоящий запрос
с заведомо неверным токеном и разбирает JSON в теле ответа.

```
{"ok":false,"error_code":401,"description":"Unauthorized: invalid token specified"}
```

`401` здесь — не ошибка инструмента, а признак того, что ответ
Telegram дошёл. Ни один кэш и ни один балансировщик не подставляет
такую структуру.

### Переживает ли перезагрузку

Да. `fix` пишет `/usr/local/sbin/telegram-route-fix.sh` и
`/etc/systemd/system/telegram-route-fix.service`, включает автозапуск.

Здесь важно не остановиться на «правило применено». Скрипт
автозапуска и применённое правило — две разные вещи, и в первой
сборке инструмента первое было сломано, а второе работало. Бот
молчал бы после перезагрузки, и обнаружилось бы это через месяц.

Поэтому `fix` после запуска службы **проверяет, что служба active**,
и возвращает код 6 с предупреждением, если она не поднялась:

```
автозапуск: enabled, служба: failed
...
ИТОГ: сейчас работает, после перезагрузки — нет.
      Чинить надо до перезагрузки, а не после.
```

Разбор при этом не гадается, а печатается:

```bash
bash -n /usr/local/sbin/telegram-route-fix.sh
/usr/local/sbin/telegram-route-fix.sh
journalctl -u telegram-route-fix.service -n 20 --no-pager
```

### Чего инструмент не делает

- не трогает маршрут по умолчанию
- не трогает интерфейсы `awg0` / `wg0`
- не пишет в `/etc/hosts`
- не отправляет сообщений и не вызывает `getUpdates`

Число пиров на туннеле измеряется до и после, и расхождение
выводится как предупреждение, а не остаётся незамеченным.

## Ограничение, о котором надо знать заранее

Список адресов Telegram зашит в инструмент. Telegram вправе сменить
их в любой момент, и тогда зашитое станет неверным.

Поэтому есть `verify`: она говорит, жив ли адрес, на который сейчас
настроено перенаправление. Если `verify` сказал «мёртв» — нужен
новый запуск `fix`, который переберёт список заново.

Следить за этим стоит не вручную, а по расписанию: если бот
внезапно замолчал, а `verify` вернул «мёртв», дело не в боте.

## Смежная находка: LLM с российского адреса не работает вообще

Раз уж речь о ботах, стоит записать и вторую вещь — она того же
рода и тоже неочевидна.

Проверено **тем же ключом** с двух адресов: телефон выходит через
Cloudflare WARP в Латвии, сервер — из российского дата-центра.
Сервер представляется как `loc=RU`.

| Провайдер | с Латвии | с российского адреса |
|---|---|---|
| openrouter.ai | `200`, ответ «OK» | `403` Access denied by security policy |
| api.z.ai | работает | `429` Insufficient balance |
| api.mistral.ai | работает | `429` на всех ключах |
| api.groq.com | работает | `403` |
| integrat.api.nvidia.com | работает | `410 Gone` |
| generativelanguage.googleapis.com | — | TCP не проходит вовсе |

Ключи одинаковые, отличается только адрес выхода. Значит причина не
в ключах и не в настройке запроса, а в географии.

### Главное: блокируются и платные

Это проверено отдельно, потому что естественно предположить, что
«бесплатные уровни закрыты для России, а за деньги откроют».
Не откроют. Ответ приходит **до проверки ключа**, тело ответа
показывает причину дословно:

```
api.openai.com
  {"error":{"code":"unsupported_country_region_territory",
            "message":"Country, region, or territory not supported",
            "type":"request_forbidden"}}

api.anthropic.com
  {"error":{"type":"forbidden","message":"Request not allowed"}}

openrouter.ai
  {"success": false, "error": "Access denied by security policy."}
```

Запрос с заголовком `Authorization: Bearer sk-invalid` даёт **тот же**
ответ. То есть до авторизации дело не доходит: соединение
разрешено, TLS согласован (0,35 с), а решение принимается на
границе по стране.

**Следствие, которое важно не перепутать с настройкой.** Деньги
здесь не помогут. Ключ за любую цену будет отвергнут, потому что
отвергается не он, а адрес.

### Как тогда читать коды ответа

Разбирать надо внимательно. `429` и `400` — это **успешная
авторизация**: ключ прошёл проверку и упёрся в лимит или в неверное
имя модели. Считать любой не-200 мёртвым ключом — выбросить
рабочие ключи.

Порядок разбора:

| Код | Что означает |
|---|---|
| `200` | ключ рабочий |
| `400` | ключ рабочий, неверное имя модели |
| `401` | ключ отвергнут, либо нет заголовка |
| `403` + текст про страну | ключ ни при чём, закрыт адрес |
| `403` без пояснения | смотреть тело ответа |
| `410` | эндпоинт объявлен мёртвым |
| `429` | ключ рабочий, лимит исчерпан |

### Что из этого следует для SORA

Функции, которым нужна только доставка, на сервере работают.
Функции, которым нужен LLM, с российского адреса не заработают —
ни на бесплатных ключах, ни на платных.

Обойти это настройкой нельзя: не поможет ни смена заголовков, ни
повтор, ни прокси до зарубежного API-шлюза, если сам адрес
остаётся российским.

Что поможет — только смена адреса выхода:

1. Пропускать трафик к LLM через туннель с зарубежным выходом.
   Работает, но добавляет зависимость: нужно держать туннель живым
   и следить, в какой стране он выходит.
2. Держать LLM-часть не на этом сервере.

Это ограничение внешних сервисов, а не настройка сервера.
