# ЧАСТЬ 0. ЧТО ГДЕ ЛЕЖИТ

```
SORA/
├── tools/          ← генератор ключей и диагностика (нужен ВЛАДЕЛЬЦУ)
│   ├── sora_keys.py         генератор ключей и конфигов
│   ├── sora_doctor.py       диагностика всего (25 проверок)
│   ├── sora_client_check.py проверка с клиента
│   └── sora_traffic.py      учёт трафика (копируется на сервер)
│
└── server/         ← установщик (нужен АДМИНИСТРАТОРУ)
    ├── install_sora.sh      главный установщик, 15 шагов
    ├── sora-selftest.sh     проверка правильности установки
    ├── sora-health.sh       проверка состояния
    ├── sora_backup.sh       резервное копирование ключей
    ├── sora-open-port.sh    открыть порт для трекера
    ├── sora-close-port.sh   закрыть порт для трекера
    └── uninstall_sora.sh    полный откат
```

**Кто что делает:**

- **Владелец** (вы) — части 2 и 7, на своём ноутбуке.
- **Администратор** — части 1, 3, 4, 5, 6, 8.

**Передаётся администратору ровно один файл:** `server/server.conf`.
Клиентские конфиги остаются у вас — администратору они не нужны.

# ЧАСТЬ 1. ПРОВЕРИТЬ СЕРВЕР ДО УСТАНОВКИ

Зайдите на сервер по SSH под пользователем с правами `sudo`.
Все команды в частях 1, 4, 5, 6, 8 выполняются **на сервере от root**.

## 1.1. Кто я

```bash
whoami          # ожидаем: root
# либо, если вы не root:
sudo -i         # перейти в root и дальше работать от него
```

## 1.2. Система

```bash
cat /etc/debian_version
```

Ожидаем: `12.x`. Установщик рассчитан именно на Debian 12.
На других дистрибутивах может не сработать `apt-get`.

## 1.3. Память — самое узкое место

```bash
free -m
```

Ожидаем строку `Mem:` со значением **available** не меньше **150**.

150 — это порог, который проверяет установщик (`install_sora.sh`,
шаг 0). Ниже него он откатится и ничего не поставит.

Для ориентира: на сервере SORA свободно около **440 МБ** из 708.
Сам VPN ест 40–80 МБ, unbound ещё 20–30 МБ. Запас есть, но сервер
небольшой — если available ниже 300 МБ, стоит сначала понять, что
занимает память.

Раньше в этой инструкции было написано «не меньше 400». Это было
неверно: 400 — запас, который никто не проверяет, а не требование.
Установщик требует 150, и проверка `sora-selftest.sh` предупреждает
ниже 200.

## 1.4. Место на диске

```bash
df -h /
```

Ожидаем свободно **≥ 3 ГБ**.

## 1.5. Порт свободен

```bash
ss -lun | grep 39117
```

Ожидаем: **пусто**. Если строка есть — порт кем-то занят.
Скрипт установки откажется, это правильное поведение.

> **Не путайте с проверкой извне.** Все TCP-порты на этом IP
> отвечают — так работает анти-DDoS фильтр провайдера. Поэтому
> проверка порта снаружи сервера **ничего не значит**. Проверять
> надо именно так, как выше, изнутри.

## 1.6. Пересылка пакетов

```bash
sysctl net.ipv4.ip_forward
```

Ожидаем: `1`. Если `0` — установщик это включит сам, проверить
можно после установки.

## 1.7. Проверка себя

Ответьте себе, все ли пункты «да»:

- [ ] есть доступ по SSH
- [ ] система Debian 12
- [ ] свободно ≥ 150 МБ памяти
- [ ] свободно ≥ 3 ГБ на диске
- [ ] порт 39117/UDP свободен
- [ ] понял: **перезагрузка сервера не требуется**
- [ ] понял: **nginx и трекер трогать нельзя**

# ЧАСТЬ 2. СГЕНЕРИРОВАТЬ КЛЮЧИ У СЕБЯ НА НОУТБУКЕ

Эта часть — на **вашем компьютере с Windows**. Никаких прав
администратора не нужно.

Откройте PowerShell и перейдите в папку `tools`:

```powershell
cd C:\путь\к\SORA\tools
```

## 2.1. Проверить, что Python есть

```powershell
python --version
```

Ожидаем: `Python 3.x`. Если не найдено — поставьте с python.org
и **включите галочку «Add Python to PATH»**.

## 2.2. Создать реестр

```powershell
python sora_keys.py init --server-ip 203.0.113.10 --port 39117
```

Ожидаем:

```
  Реализация Curve25519 верна — сверена с библиотекой cryptography:
  40 обменов и 10 проверок симметрии.

  Реестр создан.
  файл   : ...\SORA\client\registry.json
  сервер : 203.0.113.10:39117
  подсеть: 10.77.0.0/24

  Публичный ключ сервера (понадобится в ТЗ):
  XXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXX=
```

**Запишите публичный ключ сервера** — он есть и в файле
`registry.json`, и в готовом `server.conf`.

> Реестр создаётся с правами только на вас. Файл содержит
> приватные ключи — **это и есть ваш VPN**. Потеряете реестр —
> придётся выпускать ключи заново и переустанавливать у всех.

## 2.3. Добавить людей

По одному на человека:

```powershell
python sora_keys.py add ivan  --note "ноутбук"
python sora_keys.py add masha --note "телефон"
```

Ожидаем для каждого:

```
  Добавлен: ivan
  адрес      : 10.77.0.2/32
  публичный  : XXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXX=
```

Имя — **только латиница, цифры, дефис и подчёркивание**, до 32
символов. Русские имена будут отклонены: имя попадает в
`server.conf`, а конфиг должен оставаться переносимым между
Windows и Linux.

Адрес можно задать вручную, если адрес уже занят не тем:

```powershell
python sora_keys.py add ivan --ip 10.77.0.9 --note "ноутбук"
```

Адрес должен лежать внутри `10.77.0.0/24` и быть **одним хостом**
(`/32`). Значение вроде `0.0.0.0/0` будет отклонено — в
`AllowedIPs` оно означало бы маршрут всего трафика на этого человека.

## 2.4. Отозвать человека

Если ключ утёк или человек больше не нужен:

```powershell
python sora_keys.py revoke ivan
```

Человек отключается, но не удаляется — вернуть можно.
Затем обязательно пересоберите серверный конфиг (2.6).

## 2.5. Посмотреть, что есть

```powershell
python sora_keys.py list
```

## 2.6. Собрать серверный конфиг

```powershell
python sora_keys.py server --out ..\server\server.conf
```

Ожидаем:

```
  Записан: ..\server\server.conf
  Файл содержит приватные ключи ВСЕХ клиентов и сервера.
  Передавать его нельзя. На сервер — по scp, права 600.

  Клиентов в конфиге: 2
```

**Это единственный файл, который уходит администратору.**

## 2.7. Выгрузить конфиг конкретного человека

Каждому человеку — его собственный файл:

```powershell
python sora_keys.py config ivan --out ivan.conf
```

## 2.8. Проверить, что всё собралось правильно

```powershell
python sora_doctor.py
```

Ожидаем строку вида:

```
  проверок: 25    ок 12    проблем 0    не проверено 11
```

Требование: **`проблем 0`**.

> **Дословно «Реестр в порядке» не будет.** Доктор не печатает
> такую фразу — итог смотрите по числу `проблем`. Сообщения
> Python-инструментов на русском, сообщения bash-скриптов —
> латиницей (`Vse v poryadke.`, `pamyat:`). Это сделано намеренно:
> bash не принимает кириллицу в именах переменных, и чтобы
> вести себя одинаково, текст тоже сделан латиницей.

Часть проверок покажет «не проверено» — это нормально. Это значит
«проверка не выполнена», а не «всё хорошо». Например, сетевую
проверку с клиента мы делаем уже после установки (часть 7).

> Если `проблем` не ноль — **не идите дальше**. Прочитайте вывод,
> исправьте, повторите. Устанавливать сломанный конфиг смысла нет.

# ЧАСТЬ 3. ПЕРЕДАТЬ КОНФИГ НА СЕРВЕР

## 3.1. Скопировать на сервер

```powershell
scp ..\server\server.conf root@203.0.113.10:/root/
```

Введите пароль root. Подтвердите отпечаток сервера, если спросит —
сверьте его с тем, что показывает провайдер.

## 3.2. На сервере: положить на место и закрыть права

```bash
mkdir -p /etc/sora
chmod 700 /etc/sora
mv /root/server.conf /etc/sora/server.conf
chmod 600 /etc/sora/server.conf
```

## 3.3. Проверить права

```bash
ls -la /etc/sora/
```

Ожидаем **ровно** так:

```
-rw------- 1 root root ... server.conf
```

Права `600`, владелец `root`. Если видите `-rw-r--r--` (644) —
права выставили неверно, повторите `chmod 600`.

## 3.4. Убедиться, что файл не битый

```bash
head -3 /etc/sora/server.conf
grep -c '^\[Peer\]' /etc/sora/server.conf
```

Ожидаем: первая строка `[Interface]`, а количество `[Peer]` равно
числу людей из шага 2.3 плюс один — сам сервер не считается,
клиентов должно быть ровно столько, сколько вы добавили.

# ЧАСТЬ 4. УСТАНОВИТЬ

## 4.1. Положить скрипты на сервер

Скопируйте папку `server` целиком:

```powershell
scp -r ..\server root@203.0.113.10:/root/
```

На сервере появится `/root/server/`.

## 4.2. Сделать скрипты исполняемыми

```bash
chmod +x /root/server/*.sh
chmod +x /root/server/*.py 2>/dev/null
```

## 4.3. Запустить установку

```bash
cd /root/server
bash install_sora.sh
```

Скрипт идёт 15 шагов и печатает каждый. Время — примерно
3–5 минут, из которых основное уходит на скачивание бинарника VPN.

### Что он делает по шагам

| Шаг | Что происходит |
|---|---|
| 0 | Проверки **до** любых изменений: память, место, порт |
| 1 | Подготовка и снимок сетевых настроек для отката |
| 2 | Установка пакетов: `curl`, `ca-certificates`, `iptables`, `unbound`, `jq`, `cron`, `python3` |
| 3 | Скачивание `amnezia-awg-go` с GitHub и проверка версии |
| 4 | Ограничения ресурсов для службы |
| 5 | Включение пересылки пакетов |
| 6 | Резолвер DNS внутри туннеля + проверка его конфигурации |
| 7 | Правила сети: `iptables`, `ip6tables`, `net.ipv4.ip_forward` |
| 8 | Создание службы VPN с ограничениями доступа |
| 9 | Таймер проверки состояния каждые 5 минут |
| 10 | Учёт трафика по людям |
| 10b | Резервное копирование ключей |
| 11 | Запуск службы |
| 12 | Проверка, что после установки всё живо |
| 13 | Самопроверка правильности установки |

**При любой неудаче скрипт откатывает сам** и говорит, что именно
сделал. Это не мешает вам читать сообщение.

## 4.4. Что установщик НЕ делает

Важно знать, чтобы не искать:

- не перезагружает сервер;
- не ставит Docker;
- не трогает nginx и трекер;
- не меняет настройки ядра, кроме пересылки пакетов;
- не удаляет ни одного существующего правила `iptables`.

## 4.5. Если установщик упал

Читайте последнюю строку ошибки. Типичные причины:

| Сообщение | Причина | Что делать |
|---|---|---|
| `не хватает памяти` | занято больше, чем ожидалось | `free -m`, разобраться, что занимает |
| `порт 39117 занят` | порт уже слушается | `ss -lun \| grep 39117`, освободить |
| `мало места` | диск заполнен | `df -h /`, `du -sh /var/*` |
| `нет доступа к репозиторию` | сеть/DNS сервера | проверить `ping 8.8.8.8`, `apt-get update` |

Откат, если нужно начать заново:

```bash
cd /root/server
bash uninstall_sora.sh
```

# ЧАСТЬ 5. ОБЯЗАТЕЛЬНЫЙ ШАГ: netfilter-persistent

Этот шаг **пропускают чаще всего**, и он ломает всё на следующий день.

## 5.1. Зачем

Правила `iptables`, которые мы настроили, живут **в памяти**.
При перезагрузке сервера их не станет. VPN перестанет принимать
трафик, DNS перестанет отвечать, счётчики исчезнут.

На первый взгляд всё работает — и работает неделями. А потом вы
перезагружаете сервер (или провайдер делает это сам при
обслуживании), и VPN молча умирает.

## 5.2. Сделать правила постоянными

```bash
apt install -y netfilter-persistent
```

Во время установки спросят, продолжать ли работу с
`iptables-persistent`. Ответьте **`yes`**.

Затем сохранить текущие правила:

```bash
netfilter-persistent save
```

Ожидаем: `iptables-save > /etc/iptables/rules.v4`
и то же для `.v6`. Ошибок быть не должно.

## 5.3. Убедиться, что правила сохранены

```bash
ls -la /etc/iptables/
```

Ожидаем два файла: `rules.v4` и `rules.v6`.

### ВАЖНО: проверьте плагины, а не только пакет

На Debian 12 пакет `netfilter-persistent` ставится с **пустым
каталогом плагинов**. Команды `save` и `start` в этом случае
ничего не делают, но возвращают код 0 — выглядит как успех.

```bash
ls -la /usr/share/netfilter-persistent/plugins.d/
```

Ожидаем **два файла**: `iptables` и `ip6tables`.

Если каталог пуст, установщик SORA сам доставит туда плагины из
папки `server/nfp-plugin-*`. Если ставите вручную — положите их
туда из комплекта:

```bash
cp nfp-plugin-iptables  /usr/share/netfilter-persistent/plugins.d/iptables
cp nfp-plugin-ip6tables /usr/share/netfilter-persistent/plugins.d/ip6tables
chmod 755 /usr/share/netfilter-persistent/plugins.d/iptables
chmod 755 /usr/share/netfilter-persistent/plugins.d/ip6tables
```

Без этого правила живут только в памяти: месяц всё работает, а
после перезагрузки VPN молча умирает.

## 5.4. Проверить, что они включатся при загрузке

```bash
systemctl is-enabled netfilter-persistent
```

Ожидаем: `enabled`.

Если `disabled`:

```bash
systemctl enable netfilter-persistent
```

## 5.5. Доказать, что правила переживут перезагрузку

Проверка «файл существует» ничего не доказывает. Проверим по-настоящему:
снимем правила, снесём все, попросим службу их восстановить.

```bash
iptables-save > /tmp/страховка.rules      # на всякий случай

iptables -F && iptables -X
echo "цепочек SORA после очистки: $(iptables -t filter -S | grep -c SORA-TRAFFIC)"
# ожидаем 0 — правил действительно нет

systemctl restart netfilter-persistent
echo "цепочек SORA после restart: $(iptables -t filter -S | grep -c SORA-TRAFFIC)"
# ожидаем 3 — правила вернулись

rm -f /tmp/страховка.rules
```

Если вернулось 3 — механизм работает, сервер можно перезагружать.
Если 0 — **не перезагружайте сервер**, VPN не поднимется.

## 5.6. Чек-лист этого шага

- [ ] `netfilter-persistent` установлен
- [ ] **плагины `iptables` и `ip6tables` лежат в `plugins.d`**
- [ ] `netfilter-persistent save` выполнен, файлы не пустые
- [ ] `/etc/iptables/rules.v4` и `rules.v6` существуют и не пусты
- [ ] `systemctl is-enabled netfilter-persistent` → `enabled`
- [ ] **проба с очисткой правил пройдена** (шаг 5.5)

> **Проверка после перезагрузки.** Когда будет возможность,
> перезагрузите сервер и убедитесь, что VPN поднялся:
> `systemctl is-active amnezia-awg-go` → `active`.

# ЧАСТЬ 6. ПРИЁМКА НА СЕРВЕРЕ

Не считайте установку успешной, пока не пройдёте этот раздел.

## 6.1. Проверка состояния

```bash
bash /root/server/sora-health.sh
```

Ожидаем строку **`Vse v poryadke.`** (латиницей — в bash-скриптах
сообщения транслитерированы) и код возврата **0**.

Проверить код:

```bash
bash /root/server/sora-health.sh >/dev/null 2>&1; echo "код: $?"
```

Ожидаем: `код: 0`. Код `1` означает, что есть проблемы, — читайте
вывод выше по скрипту.

## 6.2. Службы живы

```bash
systemctl is-active amnezia-awg-go     # active
systemctl is-active unbound            # active
systemctl is-enabled sora-health.timer # enabled
```

## 6.3. Порт слушается

```bash
ss -lunp | grep 39117
```

Ожидаем строку с `amneziaawg` и адресом `*:39117`.

## 6.4. Память в норме

```bash
free -m
```

Ожидаем: available **> 150 МБ**. Если ниже — VPN работает впритык,
разберитесь до того, как пользуются.

## 6.5. Учёт трафика — и здесь легко получить ложное «всё хорошо»

```bash
python3 /root/server/sora_traffic.py poll; echo "код: $?"
```

Ожидаем код **0 или 1**. 

**Не 2.** Код 2 означает, что счётчики не создались.

Теперь таблица:

```bash
python3 /root/server/sora_traffic.py report
```

**Проверьте руками, что счёт не нулевой.** Если у всех нули —
значит счётчики не встали. Проверьте:

```bash
iptables -t filter -L SORA-TRAFFIC -n -v -x
```

Должны быть правила. Их нет — установка прошла не полностью,
вернитесь к шагу 13 установщика.

> **Почему это проверяется отдельно.** Установка может закончиться
> кодом 0, служба жива, всё зелёное — а счётчики не создались.
> Тогда месяц VPN работает, люди подключаются, а трафик не
> посчитан ни байтом. Проверка состояния этого не заметит:
> служба-то действительно работает.

## 6.6. CSV-выгрузка

```bash
cat /var/lib/sora/traffic.csv
```

Ожидаем: файл существует и не пуст.

## 6.7. Резервная копия

```bash
bash /root/server/sora_backup.sh list
ls -la /var/backups/sora/
```

Ожидаем: каталог с правами `700`, копии внутри — с правами `600`.
Проверьте права файлов:

```bash
ls -la /var/backups/sora/*/server.conf
```

## 6.8. Автоматика на месте

```bash
cat /etc/cron.d/sora
```

Ожидаем **три задачи**:

| Что | Когда | Команда |
|---|---|---|
| учёт трафика | каждые 5 минут | `sora_traffic.py poll` |
| резервная копия | в 04:17 | `sora_backup.sh` |
| проверка состояния | каждые 15 минут | `sora-health.sh --tiho` |

## 6.9. Самопроверка — самая важная проверка приёмки

```bash
bash /root/server/sora-selftest.sh
```

Ожидаем строку вида:

```
  ПРОВЕРЕНО 30    ок 30    ошибок 0    пропущено 5
```

Требование: **ошибок 0**.

**Смотрите внимательно на `пропущено`.** Пропуски бывают двух
разных сортов, и это не одно и то же:

| Что пропущено | Это нормально? |
|---|---|
| `free недоступна` | да, вы не на Linux |
| `нет tracker.services` | нет — трекер должен остаться |
| `${SVC} не установлен` | **нет** — VPN не установлен |
| `учёт трафика не установлен` | **нет** — это часть SORA |
| `iptables нет, счётчики не проверяем` | **нет** — счётчики не проверяются |

На рабочем сервере с установленным SORA и живым трекером
ожидается **ноль пропусков**. Если в `пропущено` есть строки из
нижней половины таблицы — установка неполная, идите в раздел 9.

Каждая отдельная проверка помечена `[ок]`, пропущенные — `[--]`.
Строка `--tiho` печатает только проблемы — так работает таймер.

Она видит то, чего не видит проверка состояния:

- счётчики трафика заведены на **каждого** пользователя, а не просто
  создана цепочка;
- у каждой секции `[Peer]` есть имя — без него учёт не знает, кому
  принадлежит трафик, и припишет его ничему;
- права на копии ключей: 600 на файлы, 700 на каталог;
- `Restart=on-failure` и автозапуск включены;
- три задачи в `/etc/cron.d/sora` на месте;
- правила сети сохранены и переживут перезагрузку;
- трекер из `tracker.services` работает.

# ЧАСТЬ 7. ПОДКЛЮЧИТЬ КЛИЕНТА

Эта часть — **на вашем ноутбуке**.

## 7.1. Установить клиент

Подойдёт AmneziaWG. Версию мы не фиксировали: формат конфига
стандартный, работает с обычным WireGuard-совместимым клиентом,
который понимает параметры Amnezia (`Jc`, `Jmin`, `Jmax`, `S1`,
`S2`, `H1`–`H4`).

## 7.2. Получить конфиг

Если делали в шаге 2.7 — файл `ivan.conf` уже есть. Иначе:

```powershell
python sora_keys.py config ivan --out ivan.conf
```

## 7.3. Подключиться

Вставьте содержимое `ivan.conf` в клиент, подключитесь.

## 7.4. Проверить, что адрес наш

Откройте в браузере:

```
https://whatismyipaddress.com
```

Ожидаем: **203.0.113.10**

Если видите другой адрес — вы смотрите не на SORA. Возможно, активен
WARP. Это не поломка, но проверка должна идти при выключенном WARP.

> **WARP и SORA — не взаимозаменяемые вещи.** WARP даёт общий адрес
> Cloudflare, SORA — ваш собственный. Они дополняют друг друга.
> При проверке адреса отключите WARP, иначе результат будет
> неоднозначным.

## 7.5. Проверить, что DNS не утекает

```
https://ipleak.net
```

Ожидаем: DNS-серверы **не российские**, они из подсети `10.77.0.x`.

Если видите российские DNS — утечка. Это значит, что запросы идут
мимо туннеля, и провайдер видит ваши домены.

## 7.6. Проверить, что трафик идёт

Откройте любой сайт. Работает — значит маршрутизация верна.

## 7.7. Автоматическая проверка с клиента

```powershell
python sora_client_check.py
```

Она проверяет то же самое, но с отчётом: какой адрес снаружи,
какие DNS видны, есть ли утечка IPv6. И отдельно различает SORA
и WARP — чтобы вы не гадали, что именно сейчас подключено.

## 7.8. Убедиться, что трафик посчитан

На сервере, через 5 минут после подключения (после опроса):

```bash
python3 /root/server/sora_traffic.py report
```

Счёт человека должен быть ненулевым. Если ноль — вернитесь к
шагу 6.5 и проверьте счётчики.

## 8.1. Ограничить трафик человеку

По умолчанию лимитов нет — трафик просто считается.

```bash
python3 /root/server/sora_traffic.py limit ivan 100   # 100 ГБ/мес
python3 /root/server/sora_traffic.py limit --list      # показать все
python3 /root/server/sora_traffic.py limit ivan        # снять лимит
python3 /root/server/sora_traffic.py apply            # применить сейчас
python3 /root/server/sora_traffic.py restore ivan     # вернуть человека
```

Отключение по лимиту вступает в силу при следующем опросе — не
позже чем через 5 минут, либо сразу после `apply`.

## 8.2. Убрать отключение, если человек не виноват

```bash

```

# ЧАСТЬ 9. ЕСЛИ ЧТО-ТО НЕ ТАК

| Симптом | Вероятная причина | Что делать |
|---|---|---|
| VPN не подключается | не открыт порт | `ss -lunp \| grep 39117` |
| после перезагрузки VPN умер | **не сделан** шаг 5 | `netfilter-persistent save` |
| трафик не считается | не создались счётчики | `iptables -t filter -L SORA-TRAFFIC -n -v -x` |
| DNS утекает в российские | unbound не слушает `10.77.0.1` | `ss -lunp \| grep :53` |
| сайт открывается, но IPv6 «течёт» | в конфиге убран `::/0` | `sora-selftest.sh` покажет |
| `poll` возвращает 2 | счётчики не установлены | см. строку выше |
| память кончилась | мало свободной памяти | `free -m`, остановить лишнее |
| порт не открывается снаружи | анти-DDoS фильтр провайдера | проверить **изнутри**, см. 1.5 |
| установщик откатился | сработала проверка в шаге 0 | читать последнюю строку ошибки |

## 9.1. Полный откат

Убрать всё и вернуть сервер в исходное состояние:

```bash
cd /root/server
bash uninstall_sora.sh
```

Скрипт снимет службу, таймер, cron-задачи, правила сети и
восстановит настройки из снимка, сделанного в шаге 1 установщика.

## 9.2. Что делать НЕ надо

- **Не перезагружать** сервер «для применения настроек» — не нужно.
- **Не трогать** nginx и трекер. Установщик их не трогает, и вам не
  надо. Если после установки трекер перестал работать — значит, дело
  не в установке.
- **Не удалять** правила `iptables`, которые вы не создавали.
- **Не класть** `server.conf` в общий каталог и не пересылать его
  по почте.
